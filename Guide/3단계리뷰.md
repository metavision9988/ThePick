# 🔍 VOID DEV HARNESS — Code Review Prompts

## 규모별 3단계 코드 점검 프롬프트

> **핵심 교훈:** "리뷰하라"고 하면 AI는 컴파일 에러만 본다.
> "이 코드가 프로덕션에서 사용자 10,000명을 받았을 때 어디서 터지는가?"라고 하면
> 비로소 진짜 문제를 찾는다.
>
> 질문이 구체적일수록 분석이 깊어진다.

---

## 사용법

```
규모를 판단하고 해당 프롬프트를 Claude Code에 붙여넣는다.

  단일 모듈 수정 (함수 1~3개, 파일 1~2개) → Level 1
  서비스/기능 단위 (파일 5개+, 모듈 연계)  → Level 2
  전체 서비스 / 배포 전 / Phase 완료       → Level 3

★ 프롬프트 내의 {중괄호}는 실제 값으로 바꿔서 사용.
★ 그대로 붙여넣어도 동작하지만, 구체적 경로를 넣을수록 분석이 정확해진다.
```

---

## Level 1: 단일 모듈 점검

**적용:** 함수 1~3개 수정, 파일 1~2개 변경 후

```
방금 구현한 코드를 5가지 관점에서 점검해줘.
단순 컴파일/타입 에러가 아니라 "프로덕션에서 터지는 경로"를 찾는 것이 목표다.

## 점검 대상
{수정한 파일 경로 — 예: src/lib/transfer.ts}

## 관점 1 — 파괴자 (이 코드를 깨뜨려라)
나는 이 함수를 고장내려는 테스터다.
- null, undefined, 빈 문자열, 빈 배열, NaN, Infinity를 넣으면?
- 네트워크가 요청 중간에 끊기면?
- 동시에 2번 호출하면?
- 입력이 기대 크기의 100배면?
각 경우에 코드가 어떻게 반응하는지 추적하고, 크래시 경로가 있으면 코드 위치와 함께 보고해라.

## 관점 2 — 배관공 (데이터 흐름을 추적해라)
이 함수의 입력이 어디서 오고, 출력이 어디로 가는가?
- 입력 데이터의 shape이 변하는 모든 지점을 나열
- 타입 단언(as)이나 non-null 단언(!)이 있으면 각각 "이것이 거짓이 되는 시나리오"를 제시
- async 함수면: await 누락, 에러 전파 경로, Promise 체인이 끊기는 지점 확인
- 반환값이 null/undefined가 될 수 있는데 호출자가 체크하지 않는 경우

## 관점 3 — 회계사 (자원을 추적해라)
- 열린 것은 닫히는가? (파일 핸들, DB 커넥션, 이벤트 리스너, setInterval, WebSocket)
- 에러 경로에서도 자원이 해제되는가? (try-finally 또는 using)
- 메모리: 클로저가 큰 객체를 캡처하고 있지 않은가?
- 타이머/리스너가 컴포넌트 언마운트 후에도 살아있지 않은가?

## 관점 4 — 프로젝트 전문가 (맥락을 확인해라)
이 프로젝트의 CLAUDE.md와 .claude/rules/dev-guide.md를 읽고:
- Hard Limit을 위반하는 부분이 있는가?
- 기존 코드베이스의 패턴/컨벤션과 다르게 구현한 부분이 있는가?
- 이 모듈이 의존하는 암묵적 전제 (예: "인증된 사용자만 호출한다")가 코드에 assertion으로 명시되어 있는가?

## 관점 5 — 미래의 나 (6개월 후에도 이해되는가)
- 함수명/변수명이 동작을 정확히 설명하는가?
- 매직 넘버가 상수로 추출되어 있는가?
- 복잡한 로직에 "왜 이렇게 했는가" 주석이 있는가?
- 함수가 20줄을 넘으면 분리할 수 있는가?

## 보고 형식
각 관점에서 발견한 것을 심각도별로 분류:

🔴 Critical — 프로덕션에서 크래시/데이터 손실 가능. 즉시 수정.
🟠 Major — 특정 조건에서 오작동. 배포 전 수정.
🟡 Minor — 개선하면 좋지만 동작에 영향 없음.

★ 관점마다 "발견 없음"이면 구체적 이유를 한 줄로. "없음"만 쓰지 마라.
★ 🔴 Critical이 있으면 수정 코드까지 제시해라.
```

## Level 2: 서비스/기능 단위 점검

**적용:** 파일 5개+, 여러 모듈 연계, 새 기능 완성 후

```
이번에 구현한 기능 전체를 점검해줘.
단일 파일이 아니라 "모듈 간 연계에서 터지는 문제"를 찾는 것이 목표다.

## 점검 대상
{기능 설명 — 예: 파일 수신 히스토리 기능 (localStorage 저장 + 히스토리 페이지 + 삭제)}
{수정된 파일 목록 — git diff --name-only 결과 또는 직접 나열}

## Phase A — 바텀업 (각 모듈 단독)
수정된 각 파일을 개별적으로 분석:
- 각 파일에서 Level 1의 관점 1~3 (파괴자, 배관공, 회계사) 적용
- 파일별 Critical/Major 목록 작성
- ★ 여기서 개별 파일 문제를 먼저 잡아야 Phase B가 의미 있다

## Phase B — 탑다운 (모듈 간 연계)
### B-1. 데이터 계약 (모듈 경계에서 shape이 일치하는가?)
- 모듈 A가 보내는 데이터와 모듈 B가 기대하는 데이터의 shape이 정확히 일치하는가?
- 인터페이스/타입이 공유되는가, 아니면 각자 따로 정의했는가?
- API 응답 shape이 변경되면 어떤 컴포넌트가 깨지는가?

### B-2. 이벤트 체인 (한쪽이 실패하면 다른 쪽은?)
- 모듈 A → 모듈 B → 모듈 C로 이어지는 체인에서
  B가 실패하면 A는 알 수 있는가? C는 어떻게 되는가?
- 비동기 이벤트가 순서대로 도착하지 않으면?
- 중복 이벤트가 발생하면? (멱등성)

### B-3. 상태 동기화 (여러 곳에서 같은 데이터를 다루는가?)
- 같은 데이터가 2곳 이상에서 관리되면 → 불일치 시나리오 제시
- localStorage와 서버 상태가 동시에 존재하면 → 어느 것이 진실인가?
- 상태 변경 후 UI가 즉시 반영되는가, 다음 렌더링까지 기다리는가?

### B-4. 초기화 순서 (앱 시작 시)
- 이 기능의 모듈들이 초기화되는 순서가 보장되는가?
- 모듈 B가 모듈 A에 의존하는데, A보다 B가 먼저 초기화되면?

## Phase C — 도메인 전문가 (비즈니스 로직)
이 프로젝트의 기획서/CLAUDE.md/Hard Limit을 기준으로:
- 기획서에 명시된 동작과 실제 구현이 다른 부분이 있는가? (Silent Pivot)
- 기획에 있지만 구현에서 빠진 것이 있는가? (기능 누락)
- 기획에 없지만 구현에 추가된 것이 있는가? (스코프 확장)
- Hard Limit을 위반하는 경로가 있는가?

## Phase D — 공격자 (보안 + 엣지 케이스)
- 사용자 입력이 검증 없이 DOM에 삽입되는 경로 (XSS)
- 외부 데이터가 쿼리/명령어에 직접 들어가는 경로 (Injection)
- 인증/인가 우회 가능 경로
- Rate limiting이 없는 비용 발생 API
- 파일 크기 0바이트, 이름에 특수문자, 확장자 위조

## 보고 형식

### Phase A (바텀업) 결과
| 파일 | Critical | Major | Minor |
|:---|:---:|:---:|:---:|

### Phase B (탑다운) 결과
| 연계 지점 | 문제 | 심각도 |
|:---|:---|:---:|

### Phase C (도메인) 결과
| 기획 항목 | 구현 상태 | 괴리 |
|:---|:---|:---|

### Phase D (보안) 결과
| 취약점 | 경로 | 심각도 |
|:---|:---|:---:|

★ 🔴 Critical이 있으면 즉시 수정 후 빌드/테스트 재확인.
★ "문제 없음"이면 각 Phase에서 "왜 문제가 없는지" 근거를 한 줄 제시. "없음"만 쓰지 마라.
```

## Level 3: 전체 서비스 / 배포 전 / Phase 완료 점검

**적용:** 배포 직전, Phase 완료, 또는 전면 점검 요청 시

```
이 프로젝트의 현재 상태를 전면 점검해줘.
배포 후 사용자 10,000명이 접속했을 때 "어디서 어떻게 터지는가"를 찾는 것이 목표다.

## 점검 대상
전체 프로젝트. 특히 최근 변경된 영역:
!`git log --oneline -20`
!`git diff --stat HEAD~10`

## 1단계 — 인프라 기반 점검 (자동 도구)
먼저 아래를 실행하고 결과를 분석해라:
!`npm run build 2>&1 | tail -20`
!`npm run lint 2>&1 | tail -20`
!`npm run test 2>&1 | tail -30`
!`npx tsc --noEmit 2>&1 | tail -20`

빌드/린트/테스트/타입 에러가 있으면 먼저 보고.
전부 통과하면 2단계로 진행.

## 2단계 — 아키텍처 점검 (숲을 봐라)
### 2-1. 의존성 방향
- 순환 의존(circular dependency)이 있는가?
- UI → 비즈니스 → 인프라 방향이 역전된 곳이 있는가?
- 외부 패키지 중 deprecated/취약한 것이 있는가?
  !`npm audit --production 2>&1 | tail -10`

### 2-2. 에러 처리 일관성
- 에러 처리 패턴이 프로젝트 전체에서 일관적인가?
- 빈 catch 블록이 있는가?
  !`grep -rn "catch" src/ --include="*.ts" --include="*.tsx" | grep -E "catch\s*\{?\s*\}" | head -10`
- 사용자에게 보여지는 에러 메시지가 기술 용어 대신 친절한 안내인가?

### 2-3. 데이터 흐름 전체 경로
- 사용자 입력 → 처리 → 저장 → 표시의 전체 경로를 추적
- 각 경계에서 검증이 이루어지는가?
- 검증이 클라이언트에서만 되고 서버에서 안 되는 경우는?

## 3단계 — 비기능 요구사항 점검
### 3-1. 성능
- 번들 크기가 예산 이내인가?
  !`ls -la dist/*.js 2>/dev/null || ls -la .output/**/*.js 2>/dev/null | head -5`
- N+1 쿼리 패턴이 있는가?
- 대용량 리스트 렌더링에 가상화(virtualization)가 적용되었는가?
- 불필요한 리렌더링을 유발하는 상태 관리가 있는가?

### 3-2. 동시성 / 경쟁 조건
- 같은 자원을 동시에 접근하는 경로가 있는가?
- 낙관적 업데이트 후 서버 거부 시 롤백이 되는가?
- WebSocket/SSE 재연결 시 메시지 유실 가능성은?

### 3-3. 장애 복원력
- 외부 서비스(API, DB, 스토리지)가 다운되면 앱은 어떻게 되는가?
- Graceful Degradation이 설계되어 있는가?
- Kill Switch가 있는가?

## 4단계 — 도메인 + 사용자 관점
### 4-1. 기획 대조
프로젝트 CLAUDE.md의 기능 목록과 실제 구현을 대조:
- 기획에 있지만 구현에 없는 것 (미구현)
- 구현에 있지만 기획에 없는 것 (스코프 확장)
- 구현이 기획과 다른 것 (Silent Pivot)

### 4-2. 사용자 여정
가장 핵심적인 사용자 시나리오 3개를 시뮬레이션:
- 시나리오 1: {예: 처음 방문한 사용자가 파일을 전송}
- 시나리오 2: {예: 수신자가 파일을 받아서 저장}
- 시나리오 3: {예: 네트워크 끊김 후 재연결}
각 시나리오에서 막히는 지점, 혼란스러운 지점, 에러가 발생하는 지점을 식별.

### 4-3. 보안 최종 점검
- [ ] .env / 시크릿이 코드에 하드코딩되지 않았는가?
- [ ] 모든 사용자 입력이 서버사이드에서 검증되는가?
- [ ] XSS 방어 (innerHTML 사용 금지 또는 sanitize)?
- [ ] CORS 설정이 과도하게 열려있지 않은가?
- [ ] 인증이 필요한 엔드포인트에 인증이 적용되었는가?
```

## 부록: 커맨드화 (선택)

자주 쓰는 Level을 커맨드로 등록하면 편하다.

```bash
# Level 1을 커맨드로
cp level1-review-prompt.md ~/.claude/commands/review-module.md

# Level 2를 커맨드로
cp level2-review-prompt.md ~/.claude/commands/review-feature.md

# Level 3를 커맨드로
cp level3-review-prompt.md ~/.claude/commands/review-full.md
```

사용:

```
/user:review-module    ← 단일 모듈 수정 후
/user:review-feature   ← 기능 완성 후
/user:review-full      ← 배포 전
```

## 왜 이 프롬프트가 자동 리뷰보다 효과적인가

```
자동 리뷰 (rules/에 텍스트):
  → AI가 "이미 아는 코드"를 "이미 아는 관점"으로 본다
  → 자기가 짠 코드에 자기가 점수를 준다 (TYPE-4 순환 검증)
  → "문제 없음" 4번 반복

수동 프롬프트 (구체적 질문):
  → "null을 넣으면?", "동시에 2번 호출하면?" 같은 구체적 시나리오를 강제
  → AI가 각 시나리오를 실제로 추적해야 함
  → "문제 없음"이면 "왜 없는지" 근거를 요구 → 대충 넘기기 불가

핵심 차이:
  "리뷰해라" → AI가 알아서 판단 → 대충 "OK"
  "null 넣으면 터지나?" → AI가 코드를 추적해야 함 → 실제 문제 발견
```
