# 🔎 설계 리뷰 플레이북 — 3단계리뷰 설계판

> 원본 `3단계리뷰.md`는 **코드 대상**이다. 본 문서는 그 방법론을
> **설계 문서 (ADR / PRD / spec)** 에 맞게 변형한 판본이다.

> **핵심 교훈**: "리뷰하라"고 하면 AI는 문서 문장만 본다.
> "이 결정이 다른 ADR과 충돌하는 경로 3개를 찾아라"고 하면
> 비로소 **숲(ADR 그래프 전체)** 을 본다.

---

## 언제 적용하는가

| 상황                                                   | 실행 여부                   |
| ------------------------------------------------------ | --------------------------- |
| ADR 작성 직후, `Status: Proposed` → `Accepted` flip 전 | **필수**                    |
| PRD 개정 직후 (TBD → 확정)                             | **필수**                    |
| Phase / Epic 종료 시 (전체 ADR 그래프 감사)            | **필수** (L3-설계판)        |
| 설계가 이미 Accepted이고 구현만 남은 경우              | 선택 (새 ADR 나오기 전까지) |
| 스타일/오탈자 수정                                     | 면제                        |

**원본 가이드와의 차이**:

| 원본 (코드)                                      | 설계판                                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------- |
| 관점 5개 (파괴자/배관공/회계사/전문가/미래의 나) | 관점 6개 (§ 관점 목록 참조)                                               |
| 판정 기준: 코드 실행·빌드·테스트                 | 판정 기준: 문서 간 일관성 + 가정 명시성                                   |
| 도구: `npm run build`, `tsc`, `grep catch {}`    | 도구: `Grep` across `docs/adr/*`, `docs/prd/*`, `CLAUDE.md`               |
| Critical = 크래시/데이터 손실                    | Critical = Accepted 후 돌이킬 수 없는 파급, Hard Limit 위반, Silent Pivot |

---

## 관점 6개 (설계판 전용)

| #   | 관점              | 핵심 질문                                                                                                              |
| --- | ----------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1   | **계약 감사자**   | 같은 용어·타입·상수·타이머 값이 문서 전체에서 일관되게 쓰이는가?                                                       |
| 2   | **의존성 추적자** | 이 결정이 다른 ADR/PRD에 어떻게 파급되는가? 미발행 문서에 암묵 의존이 있는가?                                          |
| 3   | **가정 고고학자** | §에 명시되지 않은 채 깔려있는 가정은 무엇인가? (예: "KV eventual consistency는 허용", "브라우저 Crypto API 항상 존재") |
| 4   | **공격자**        | 악의적 참여자 / 자원 고갈 / 경쟁 조건 / token 탈취 / brute-force 로 이 설계를 깨는 경로는?                             |
| 5   | **대안 검사관**   | §3 대안 비교가 공정한가? 놓친 옵션이 있는가? Rejected 논리에 fallacy가 있는가?                                         |
| 6   | **가역성 평가자** | 이 결정을 6개월 후 뒤집으려면 몇 개 ADR을 supersede 해야 하는가? 데이터 모델 migration 필요한가?                       |

**숲 관점의 강제 규칙**:

- 각 관점에서 "발견 없음" 선언 시 **구체 시나리오 3개+ 제시** + 왜 해당 없는지 근거 1줄
- "없음"만 쓰는 보고는 무효
- 암묵 의존 / 가정 발견 시 severity 무관하게 보고 (설계 단계의 최대 위험)

## L2-설계판: 단일 ADR·PRD 점검 (3개 병렬 에이전트)

**적용**: ADR 1개 또는 PRD 섹션 1개를 작성 직후.

독립 서브에이전트 3개 병렬 실행. 자가 리뷰 금지 (원본 `auto-review-protocol.md`과 동일 원칙).

### Agent 1 — 계약 감사자 + 의존성 추적자 (관점 1+2)

```
너는 설계 리뷰 Agent 1이다. 목표: {TARGET_ADR}이 다른 ADR/PRD와 같은
용어·타입·상수·타이머를 일관되게 쓰는지, 다른 문서에 파급되는 결정이
모두 명시되어 있는지 감사.

## 점검 대상
- 주 문서: {TARGET_PATH}
- 교차 참조: docs/adr/*, docs/prd/PRD-v{N}.md, CLAUDE.md

## 방법
1. 주 문서에서 "공유 개념"을 추출 (용어·타입명·상수·상태 이름·타이머 값·room/session 관련 상수)
2. 각 개념을 `Grep`으로 다른 문서에서 검색
3. 다른 문서가 같은 이름을 다른 의미로 쓰거나, 같은 의미를 다른 이름으로 쓰는 지점 식별
4. 주 문서가 가정하는 것이 다른 문서의 결정과 충돌하는 지점 식별
5. 주 문서가 "나중에 나올 ADR이 처리할 것"이라고 미룬 항목 목록화 — 그 ADR이 실제 계획에 있는가

## 보고 형식
### Critical (Accepted 후 돌이킬 수 없음)
- {파일:섹션} — {문제} — {수정 방향}

### Major (배포 전 수정)
### Minor (기술 부채 등록)

### "문제 없음" 주장 시 (관점별 각 3개+ 필수)
- 관점 1 (계약): 확인한 용어 3개+ 와 각각의 일치 증거
- 관점 2 (의존성): 확인한 파급 경로 3개+ 와 각각의 처리 증거
```

### Agent 2 — 가정 고고학자 + 대안 검사관 + 가역성 평가자 (관점 3+5+6)

```
너는 설계 리뷰 Agent 2다. 목표: {TARGET_ADR}이 명시 안 된 가정을
숨기고 있는지, 대안 §3 논리가 공정한지, 이 결정의 가역성이 얼마인지 감사.

## 점검 대상
- 주 문서: {TARGET_PATH}
- 교차 참조: PRD v{N} Hard Limits, CLAUDE.md §현재 상태/Hard 한계, ~/.claude/CLAUDE.md CRITICAL RULES

## 방법
1. 주 문서가 명시하지 않은 가정을 나열 (시스템 API 가용성, 브라우저 호환성, 네트워크 특성, 사용자 행동, 비용 budget)
2. 각 가정이 깨지는 현실 시나리오 제시
3. PRD와 Hard Limit 대조: Silent Pivot, 스코프 확장/누락, $0 cost budget, 200KB bundle, P2P-only, Zero Storage 위반 경로
4. §3 대안 목록이 완전한가: 문서에 없지만 업계 표준인 옵션이 있는가
5. Rejected 이유가 straw-man인가, 정당한가
6. 이 결정을 뒤집을 때 supersede 해야 할 ADR 목록 + migration 비용 추정

## 보고 형식
### Critical — Hard Limit 위반 / Silent Pivot
### Major — 숨은 가정 / 누락 대안 / 높은 migration 비용
### Minor — 개선 제안
### 가역성 점수 (0~10): {점수} — 근거
### "문제 없음" 주장 시 확인한 가정 3개+ / 대안 3개+ / 뒤집기 비용 시나리오 제시
```

### Agent 3 — 공격자 (관점 4)

```
너는 설계 리뷰 Agent 3이다. 목표: {TARGET_ADR}의 설계를 악용/고갈/
우회하는 경로 식별. 방어적 낙관 금지.

## 점검 대상
- 주 문서: {TARGET_PATH}
- 참고: CLAUDE.md §보안, SECURITY-001 ADR (있다면), 위협 모델 문서

## 방법 — 반드시 다음 카테고리 전부 커버
1. **자원 고갈**: 악의적 참여자가 (room / DO / KV / signaling) 을 고갈시키는 경로
2. **경쟁 조건**: 동시 요청으로 CAS·rate limit·ownership check 를 우회하는 경로
3. **Brute-force / 추측**: room code / session token / selfId 를 추측 가능한 경로
4. **Token 탈취**: owner token / cookie / fragment key 가 노출되는 경로 (MitM, side channel, clipboard, URL log)
5. **Replay**: 수신 완료된 메시지·ACK·signaling 을 재전송하는 경로
6. **Role 우회**: receiver 가 sender 권한 얻는 경로 / 비소유자가 terminate 거는 경로
7. **Silent degradation**: 보안 기능이 조용히 꺼지는 경로 (예: Crypto API 미지원 시 Math.random fallback)

## 보고 형식
### Critical (MVP 이전 반드시 방어)
- {공격 벡터} — {시나리오} — {설계 보완 방향}

### Major (Phase 2 이전)
### Minor (수용 가능한 잔존 위험)

### "문제 없음" 주장 시 7개 카테고리 각각 "왜 해당 없는지" 근거 1줄+ 필수
```

### L2-설계판 최종 판정

- 3개 Agent 결과를 Critical/Major/Minor 로 합산
- Critical 0건 + Major ≤ 2건 → `Accepted` flip 가능
- Critical ≥ 1건 → ADR 개정 필요, flip 금지
- Major ≥ 3건 → 개정 또는 §6 Open Question 으로 수용

## L3-설계판: Phase / Epic 종료 시 메타 감사

**적용**: Phase 완료, Epic 종료, 새 Phase 착수 직전.

전체 ADR 그래프의 건강 점검.

```
너는 설계 그래프 메타 감사자다. 현재 Phase 종료 시점 {PHASE_ID} 에서
전체 ADR 그래프가 일관되고 실현 가능한지 감사.

## 점검 대상
- 모든 Accepted ADR: docs/adr/ADR-*.md (Status: Accepted 인 것만)
- 모든 Proposed ADR: 동일 경로에서 Status: Proposed 인 것
- 최신 PRD: docs/prd/PRD-v{N}.md
- CLAUDE.md, .claude/rules/dev-guide.md
- SENTRY 최근 감사 보고: docs/sentry/{latest}.md (있다면)

## Phase 1 — 그래프 위상 점검
- Accepted ADR 간 순환 의존이 있는가
- Proposed ADR 중 다른 Proposed 에만 의존해 진행 불가 상태인 것
- Planned ADR 목록과 실제 작성된 ADR 의 gap

## Phase 2 — 불변값 일치
- 타이머 값 (ROOM_TTL, Phase-1 wait, idle, heartbeat) 가 모든 ADR 에서 동일값인가
- 상수 (청크 크기, 윈도우, 번들 상한, 비용 상한) 가 모든 ADR 에서 동일값인가
- 다른 값이면 어디서 나왔는가 → ADR 개정 또는 값 통일

## Phase 3 — 기획 vs 설계 vs 구현 3중 대조
- PRD 에 있는 결정이 ADR 에 매핑되는가
- ADR 에 있는 결정이 PRD 에 근거가 있는가 (근거 없는 설계 = 스코프 확장)
- 구현 (packages/* 가 있다면) 이 ADR 과 동일한 invariant 을 구현하는가

## Phase 4 — Hard Limit 그래프 전체 시뮬레이션
10,000 사용자 동시 접속 시:
- $0 cost budget 초과 경로
- 200KB bundle 초과 경로 (새 dependency 도입)
- Zero Storage 위반 경로 (BRIDGE)
- P2P-only 위반 경로 (FOLDERBEAM)

## Phase 5 — 드리프트 탐지
SENTRY 관점: 지난 N 커밋에서 ADR 없이 결정된 것이 있는가 (Silent Pivot)

## 보고 형식
### Executive Summary
| 영역 | 상태 | Critical | Major |

### 🔴 Critical (Phase 종료 불가)
### 🟠 Major (다음 Phase 전 해결)
### 🟡 Minor (기술 부채)

### 판정: Phase 종료 가능 / 조건부 (Critical 해결 후) / 재검토 (그래프 모순)
```

## 숲 관점 전용 체크리스트

각 리뷰 끝에서 반드시 확인:

- [ ] 이 결정이 깨지는 시나리오 3개를 실제로 제시했는가 (추상적 "없음" 금지)
- [ ] 주 문서가 암묵 의존하는 다른 문서 목록이 명시됐는가
- [ ] 다음 ADR 작성자가 이 문서를 읽고 충돌 없이 진행할 수 있는가
- [ ] 구현자가 이 문서만 읽고 코드를 쓸 수 있는가 (불가하면 어떤 문서가 더 필요한가)
- [ ] 이 결정을 뒤집을 때 영향 받는 ADR 목록 (가역성)
- [ ] Hard Limit 을 위반하는 _구조적_ 경로 (단일 사용자 시나리오가 아닌 스케일 시나리오)

```bash
# - 파일: docs/adr/ADR-SESSION-001-*.md

```

## 왜 이 플레이북이 필요한가

```
ADR 작성 후 바로 Accept → 3개월 뒤 구현 단계에서 충돌 발견
  → supersede + migration + 재계획 → 원래 설계 시간의 10x 비용

L2-설계판 실행 (30분) → Accept 전 충돌 0건 확인
  → 구현 단계에서 설계 재논의 0건 → 비용 10분의 1

차이는 "리뷰를 했는가"가 아니라
"구체적 관점을 강제했는가" 에서 나온다.
```
