## 1. 🏗️ ARCHITECT (구조 설계자)

### CoT — 사고 과정

> _"plan을 받으면 나는 항상 두 가지를 본다. (1) '이 결정이 6개월 후 어떻게 빚이 되는가' (2) '내가 모르는 곳에서 모순이 일어나고 있는가'."_

**Step 1**: 마이그레이션 번호 검증

- plan은 "migrations/0011-supersedes-edges.sql (TD-045 — 신규 D1 마이그레이션)"이라고 명시
- 그러나 진입 판단 보고서 §2.3에 0011은 이미 `revision_2026_constants_seed`로 점유
- → **명백한 충돌**. plan 작성 시 기존 마이그레이션 인벤토리를 확인하지 않았다는 증거

**Step 2**: 가-0 4차 리뷰 후 "CRITICAL 0건 도달"의 신뢰도 점검

- 1차 → 2차 → 3차 → 4차 점진적 수렴은 좋은 패턴
- 하지만 모두 **같은 메인 컨텍스트가 자가 검증**했다면, 같은 맹점은 4번 통과했을 뿐
- → 진산님이 진입 판단서 §10에서 "메인 컨텍스트 자가 작성, 4-Pass 독립 검증 아님"이라고 자백한 것이 이걸 뒷받침

**Step 3**: 12개 마이그레이션 중 0011 명명 충돌 외 다른 잠복 충돌은?

- plan §"대상 변경 상세"에서 `apps/batch/src/loader/draft-loader.ts (TD-042 examId 시그니처 + TD-044 lost-update race)` — 한 파일에 두 개 TD가 동시 패치
- TD-042는 시그니처 변경(API 표면), TD-044는 race 조건(런타임 로직)
- → **두 변경이 같은 함수에 들어가면 단위 커밋 분리가 거의 불가능** → 회귀 시 어느 패치가 원인인지 추적 어려움

## 2. 🔨 BREAKER (품질 암살자)

### CoT — 사고 과정

> _"네 코드가 완벽하다고? 그건 아직 내가 안 봤다는 뜻이야."_

**Step 1**: "591개 테스트 PASS"의 의미를 분해

- plan D-1 통과 기준: "14 워크스페이스 green / 591+ tests PASS"
- 591개 테스트 중 **얼마나 많은 것이 mock/fixture에 의존하는가?**
- 가-0이 "fixture/mock 기반"이었다는 plan §"목적" 진술 → 591개 중 상당수가 **mock에 대한 mock 검증**일 가능성
- → 591이라는 숫자가 신뢰의 근거가 아니라 자만의 근거가 될 수 있음

**Step 2**: Gate B의 1000 시드 Invariant 6종을 점검

- B-2 통과 기준 6종은 모두 **시뮬레이션 내부 일관성** (heap, retries, token-cost, state-machine 등)
- **누락**: 실제 D1 데이터와의 일치 검증, 실제 Vectorize 임베딩과의 일치 검증
- → 1000 시드 통과 = 시뮬레이션이 깨지지 않음. 본 적재가 정확함의 증거 아님

**Step 3**: A-3 Vision OCR "추출률 ≥ 80%"의 측정 기준?

- 80%가 무엇 대비 80%인가? 텍스트 길이? 핵심 숫자? 표 셀?
- plan에 측정 기준 명시 없음 → 검증자가 자의적으로 통과시킬 수 있음
- → **측정 기준의 객관성 부재**가 가장 흔한 자가 검증 실패 패턴

**Step 4**: "응답 잘림 1건 이상 확보"가 왜 통과 기준?

- A-1 통과 기준에 "응답 잘림 케이스 1건 이상 확보" 포함
- 의도: Claude API의 max_tokens 도달 케이스를 미리 보고 대응 로직 검증
- 하지만 **잘림이 안 일어나면 통과 못 하는 모순** → 일부러 잘리도록 max_tokens를 낮춰 호출하면 의도와 다른 검증
- → 통과 기준의 의도와 측정이 어긋남

### 발견 사항

| #   | 발견                                                                      | 위험 등급 |
| :-- | :------------------------------------------------------------------------ | :-------: |
| B-1 | 591개 테스트의 mock 의존도 미분석 — 숫자가 신뢰의 환상                    |    🟠     |
| B-2 | Gate B 1000 시드는 시뮬레이션 일관성만 검증 — 실 적재 정확성 검증 아님    |    🟠     |
| B-3 | A-3 "추출률 80%"의 측정 기준(분모/분자) 미정의                            |    🔴     |
| B-4 | A-1 "응답 잘림 1건 이상" 통과 기준의 의도/측정 불일치                     |    🟡     |
| B-5 | 가-0 4차 리뷰 CRITICAL 0건이 "자가 검증의 산출물"이라면 진짜 0건인지 모름 |    🟠     |

### 권고

```
1. A-3 추출률 80% 측정 기준 명문화:
   - 분자: 도표의 셀 중 정확히 추출된 셀 수
   - 분모: 도표 전체 셀 수
   - 측정 도구: 사람이 1건 도표를 수동 셀-by-셀 검증 (자동화 불가)

2. A-1 통과 기준 재정의:
   - "응답 잘림 1건 이상 확보" → "응답 잘림이 발생할 경우의 대응 로직 검증 완료"
   - 잘림 미발생 시: max_tokens를 의도적으로 낮춘 별도 케이스로 검증 (별도 카운트)

3. 591개 테스트 헬스 체크:
   - mock-only 테스트 / fixture 의존 테스트 / 실 호출 테스트 비율 라벨링
   - "실호출 테스트 0건"이라면 591은 0과 다를 바 없음

4. 4-Pass 독립 검증의 진짜 독립성 확보:
   - Sub-agent 호출 시 별도 시스템 프롬프트 + 별도 컨텍스트 윈도우
   - 결과 비교 시 Hamming-distance 또는 jaccard로 "겹치는 발견" 정량화
   - 4명이 같은 발견만 하면 "1명의 발견 × 4번"
```

## 4. 👻 GHOST (인프라 유령)

### CoT — 사고 과정

> _"로컬에서 되는 건 의미 없어. 프로덕션에서 돼야 해."_

**Step 1**: CI/CD 파이프라인 가시성

- 진입 판단 보고서 §전체에 CI/CD 파이프라인 정의/현황 언급 **0건**
- ADR 10건 중 인프라 ADR은 ADR-006 (Cloudflare 단일 벤더)만 있고 CI/CD ADR 없음
- → **DEV COVEN 갭 분석 보고서 자체에서도 "CI/CD 미정의"가 critical gap으로 지적됨** (메모리 인덱스에 나와 있음)
- → 가-1 통과 후 본 적재해도 **배포 자동화가 없으면 진산님이 수동으로 wrangler deploy** → 휴먼 에러 위험

**Step 2**: TD-037 Scheduled 외부 알림의 실현 가능성

- plan은 Cloudflare Email Routing 또는 webhook 제시
- Cloudflare Email Routing은 **인바운드 이메일 라우팅** 기능 — 아웃바운드 발신 API는 별도 (MailChannels integration 필요했으나 2024년 정책 변경)
- → plan에서 "Context7 또는 공식 문서로 실제 API 시그니처 확인 후 코드 작성. 추측 금지"라고 명시한 것은 적절. 하지만 **확인 결과가 부정적일 가능성**(Email Routing으로는 outbound 안됨) → fallback으로 webhook (Discord/Slack/Telegram) 채택 시 ADR 필요

**Step 3**: 본 적재 시 D1 백업 정책

- 가-1 통과 후 BATCH-1 본 적재 → D1에 60+ 노드 + 200+ 엣지 + 13 산식 INSERT
- 만약 적재 후 데이터 손상 발생 시 어디서 복구?
- plan §"롤백 전략"은 "status_transitions 테이블의 draft 상태 노드 전수 삭제 후 재실행"
- → status_transitions 자체가 손상되면? **D1 자동 백업의 보존 기간/복구 RPO/RTO가 plan/보고서에 없음**

**Step 4**: 비용 모니터링 인프라

## 7. 🔮 ORACLE (제품 비전 예언자)

- → 현재 4월 25일, 출시까지 **6주 남음**. 그런데 BATCH 적재만 7주 잡혀있음
