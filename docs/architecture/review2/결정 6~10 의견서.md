## 결정 6: 일괄 처리 임계값 (5건/3건/2건)

### 옵션 분석

| 옵션         | 일괄 처리 시작 시점                       | 결정자에게 미치는 영향        |
| ------------ | ----------------------------------------- | ----------------------------- |
| (A) 5건 이상 | 보수적 — 같은 패턴 5건 누적까지 개별 처리 | 초기 검수 시간 ↑, 안전 ↑      |
| (B) 3건 이상 | 균형 — 패턴 의심 시점 일괄 제안           | 균형 ✅                       |
| (C) 2건 이상 | 적극적 — 우연도 일괄 처리 가능            | 효율 ↑, false positive risk ↑ |

### DEV COVEN 분석

**ARCHITECT 의 패턴 신뢰성 분석:**

- 2건 = **우연 가능** (false positive 영향 2배)
- 3건 = **패턴 의심** (확률적으로 의도적 패턴)
- 5건 = **명백한 패턴** (false positive 가 5배 동시 발생할 확률 미미)

**BREAKER 의 함정 지적:**

- (C) 2건의 함정: 2건 일괄 처리 시 false positive 1건만 있어도 **2배 잘못된 결정**
- (A) 5건의 함정: 검수자가 같은 결정을 5번 반복 — alert fatigue 의 본질
- (B) 3건의 함정: 가장 균형이나, "3건 이상" 임계값 자체가 임의적

**HACKER 의 학습 곡선:**

- BATCH-1~3 시점: 진산님이 패턴 학습 중 → (A) 5건 (안전 우선)
- BATCH-4~7 시점: 패턴 인식 완료 → (B) 3건
- BATCH-8+ 시점: 효율 극대화 → (C) 2건

**ADVOCATE 의 검수 시간:**

- 5건 모이려면 검수 적체 → 사용자 응답 지연
- 3건이 균형
- 2건 일괄 처리는 검수자가 패턴을 완전히 신뢰할 때만

### 메피스토펠레스의 함정

```
함정 1 (B 의 경우):
"3건"의 임계값이 시간 windows 가 명확하지 않다.
- 같은 BATCH 내 3건? → 명확
- 같은 날 3건? → 어떤 BATCH 의 3건? 다른 패턴 섞일 수 있음
- 같은 패턴 누적 3건? → 무한 windows? 1주? 1개월?

진산님 결정 시 windows 명문화 필수.
```

```
함정 2 (모든 옵션 공통):
"일괄 처리 = 효율" 이라는 가정.
그러나 **개별 검토 = 학습 기회**.
검수자가 같은 패턴을 3번 보면, 4번째에 다른 false positive 를 발견할 수 있다.
일괄 처리는 그 학습 기회를 박탈한다.
```

### 페르소나 합의 권고

> **권고: (B) 3건 이상**
> **단,** 아래 조건 동반:
>
> - **시간 windows: 같은 BATCH 내 누적 3건** (다른 BATCH 는 별개 패턴)
> - **BATCH-1~3 동안은 (A) 5건 적용** (학습 기간)
> - **BATCH-4 부터 (B) 3건으로 전환**

**근거:**

- (A) 5건은 학습 기간에는 안전, 그 후엔 비효율
- (C) 2건은 수익보다 risk 가 큼
- (B) 3건이 통계적으로 패턴 신뢰성과 효율의 균형점

## 결정 7: AI 추천 자동 채택 (95%+ 자동/표시 후 1-click/항상 인간)

### 옵션 분석

| 옵션                     | 결정 흐름                     | 책임 소재              |
| ------------------------ | ----------------------------- | ---------------------- |
| (A) 95%+ 자동 채택       | AI → DB 자동 적용             | **AI? 시스템?** (모호) |
| (B) 95%+ 표시 후 1-click | AI 추천 → 진산님 1-click 확인 | 진산님                 |
| (C) 항상 인간 결정       | AI 표시 + 진산님 직접 결정    | 진산님                 |

### DEV COVEN 분석

**SENTINEL 의 책임 분석 (강력 반대):**

- (A) 자동 채택 = **책임 분산의 함정**
- AI 가 false 결정을 5% 확률로 내림
- 자동 채택 시 누가 책임? 진산님? Anthropic? 시스템?
- 의료/법률 분야에서 "AI 자동 결정" 은 절대 금지 패턴

**BREAKER 의 통계적 분석:**

- 95% 신뢰도 = 100건 중 5건 fail
- BATCH 14개 누적 + 큐 1 매번 30건 = 420건/14 BATCH
- → **21건 잘못 채택될 확률**
- (A) 자동 채택 시 이 21건이 **silently** 잘못 적용됨
- 24시간 Rollback 기간 내에 진산님이 이 21건을 어떻게 발견?

**ORACLE 의 비전 정합성:**

- 북극성 = "생성물 신뢰성·정확성"
- (A) 자동 채택 = 신뢰성을 AI 에 위임 → 비전 위반
- 진산님 명시: "**LLM 추론 ≠ 진실**" (Hard Rule 4 의 정신)
- → AI 추천도 추론. 검수 결정은 인간만.

**ADVOCATE 의 워크플로우:**

- (B) 1-click = 5초/건. 5초가 시스템 핵심
- (C) 항상 결정 = 결정에 더 시간 소요. AI 추천이 사실상 무용
- (B) 가 효율 + 책임 균형

**HACKER 의 구현 분석:**

- (A) 자동 채택 = 진산님이 sleep 중에도 시스템이 멋대로 결정
- 새벽 2시 BATCH-N 적재 → CBIV 통과 → 큐 1 자동 처리 → D1 INSERT
- 진산님 깨어나서 보면 이미 처리됨 → 이상한 결정 발견 → Rollback?
- 24시간 windows 안에 발견 못하면 영구 잘못

**MEPHISTO 의 종합:**

- (A) 의 함정: "효율" 이 핵심 가치 자리를 차지함
- (C) 의 함정: AI 추천이 사실상 텍스트만 보여주는 장식
- (B) 가 진짜 균형

### 메피스토펠레스의 함정

```
함정 1 (A 의 미묘한 위험):
"95% 자동 채택" 도입 → 진산님이 점점 95%+ 추천에 의존
→ 6개월 후 90% 추천도 신뢰
→ 1년 후 80% 추천도 신뢰
→ AI 추천 = 사실상 결정자
→ 진산님 = 사후 감독자 (관리자가 아닌 감시자)

이는 시스템 정체성 변질이다.
```

```
함정 2 (B 의 미묘한 위험):
1-click 채택 = "Yes" 누르기만 함
→ 진산님이 AI 추천을 실제로 검토 안 하고 채택할 수 있음
→ 1-click 의 함정: 결정의 가벼움이 사고의 가벼움 초래

해결: 95%+ 추천은 1-click 가능하나, 80~94% 는 명시적 "근거 확인" 단계 강제.
```

```
함정 3 (C 의 미묘한 위험):
"항상 인간 결정" = 자동화 가능한 부분도 인간이 담당
→ 검수자 피로감 누적 → 결국 결정 회피 (보류 누적)
→ AI 추천 무용 + 시스템 비효율

ADVOCATE 가 (C) 를 반대하는 이유.
```

### 페르소나 합의 권고

> **권고: (B) 95%+ 추천 표시 후 1-click 채택**
> **단,** 아래 조건 동반:
>
> - **80~94% 신뢰도 = 명시적 "근거 확인" 단계 강제** (1-click 금지)
> - **자동 채택은 영구 금지** (Hard Rule 격상 검토)
> - **audit log 에 AI 추천 + 인간 채택 명시 기록** (책임 투명화)
> - **월 1회 AI 추천 정확도 분석** (1-click 채택 후 Rollback 비율 monitoring)

**근거:**

- (A) 자동 채택은 SENTINEL 강력 반대 + ORACLE 비전 위반
- (C) 항상 결정은 ADVOCATE 워크플로우 비효율
- (B) 가 책임 + 효율 + 신뢰성 균형

**MEPHISTO 의 추가 안전 장치:**
신규 Hard Rule 26 신설 권장:

> **Hard Rule 26**: AI 추천의 자동 채택 금지. 모든 검수 결정은 인간의 명시적 액션 (1-click 포함) 필요. AI 추천 정확도는 월 1회 monitoring.

## 결정 8: 검수자 진행률 게임화 (담백/배지/안 함)

### 옵션 분석

| 옵션                | 표시 방식                    | 진산님에게 미치는 영향 |
| ------------------- | ---------------------------- | ---------------------- |
| (A) 진행률 + 통계만 | 객관 정보 (87/100, 4.2초/건) | 균형                   |
| (B) 배지/칭호       | "검수의 달인", 레벨 시스템   | 동기 부여 ↑, 압박 ↑    |
| (C) 일체 표시 안 함 | 큐만 표시, 통계 숨김         | 압박 ↓, 자기 인식 ↓    |

### DEV COVEN 분석

**ADVOCATE 의 양날의 검 분석:**

- 게임화 (B) = 동기 부여 ↑ but 압박 누적
- 진산님 1인 단독 = 자기 자신과 경쟁 → 자기 압박
- (B) 배지 시스템 = "오늘 50건 처리 못 하면 실패자" 인식

**ORACLE 의 비전:**

- 북극성 = 생성물 신뢰성. 처리 속도는 부수적
- 게임화 = 속도 우선 인식 → 신뢰성 저하 risk

**BREAKER 의 함정 지적:**

- (B) 게임화 = "빠르게" 처리해서 통계 개선 시도
- → Rollback 비율 낮추기 위해 결정 회피 (보류 누적)
- → 큐 적체 → 결국 시스템 정지
- 정량 지표가 함정이 되는 전형적 anti-pattern

**HACKER 의 실용 분석:**

- (C) 표시 안 함 = 진산님이 자기 진행 모름
- "내가 잘하고 있나?" 의 자기 평가 불가
- 객관 정보 (A) 가 최소 필수

**SENTINEL 의 보안 관점:**

- 게임화 (B) = 사용자 (진산님) 행동 manipulation
- 다크 패턴의 일종 (의도하지 않더라도)
- 1인 시스템에서는 부적절

**MEPHISTO 의 1인 검수자 특수성:**

- 100명 검수자 시스템 = 게임화 가능 (서로 경쟁)
- 1인 검수자 시스템 = 게임화 부적절 (자기 학대 가능)

### 메피스토펠레스의 함정

```
함정 1 (B 의 진짜 위험):
배지 시스템 = "오늘 처리 못 하면 leveling 못 함"
→ 자발적 야근
→ 피로 누적
→ 결정 품질 저하
→ 시스템 신뢰성 ↓

진산님은 본 프로젝트의 단일 SPOF.
SPOF 의 burnout = 시스템 사망.
```

```
함정 2 (A 의 미묘한 위험):
객관 정보도 압박이 될 수 있음.
"평균 4.2초/건" → "어제는 3.8초였는데..." → 자기 비교
→ 무의식적 속도 경쟁

해결: 평균/최대/최소 같은 비교 통계 대신, 단순 누적만 표시.
("오늘 87건 처리" — yes / "평균 4.2초" — no)
```

```
함정 3 (C 의 미묘한 위험):
통계 부재 = "내가 효율적인지 모름"
→ 시스템 개선 신호 부재
→ 검수 UI 자체 개선 불가능 (user feedback 없음)

해결: 통계는 시스템에 보존 (audit log) 하되, 진산님 화면에는 숨김.
요청 시만 표시 ("/stats" 명령).
```

### 페르소나 합의 권고

> **권고: (A) 진행률 + 통계만 (담백) — 단, 비교 통계 제거**
> **단,** 아래 조건 동반:
>
> - **누적 통계만 표시** ("오늘 87건 처리", "큐 1 4건 대기")
> - **비교 통계 제거** ("평균 4.2초/건" 같은 self-comparison 표시 금지)
> - **배지/칭호 영구 미도입**
> - **요청 시 상세 통계 별도 페이지** (`/admin/system/review-stats.astro` 활용)

**근거:**

- (B) 게임화는 1인 검수자에 부적절 (BREAKER + ADVOCATE + SENTINEL 합의)
- (C) 표시 안 함은 자기 인식 불가
- (A) + 비교 통계 제거 = 객관 정보 + 압박 회피

## 결정 9: Rollback 기간 (24h/7d/즉시 확정)

### 옵션 분석

| 옵션          | Rollback 기간    | 영향                            |
| ------------- | ---------------- | ------------------------------- |
| (A) 24시간    | 1일 내 취소 가능 | 균형                            |
| (B) 7일       | 1주 내 취소 가능 | 안전 ↑, Cross-BATCH 추적 어려움 |
| (C) 즉시 확정 | Rollback 없음    | 단순, 잘못된 결정 영구          |

### DEV COVEN 분석

**SENTINEL 의 안전 분석:**

- Rollback = 안전망의 본질
- (C) 즉시 확정 = 0% 안전망 → BREAKER 강력 반대
- (A) 24시간 = "잠 자고 일어나서 발견" 가능
- (B) 7일 = 너무 길어서 책임 추적 어려움

**ARCHITECT 의 Cross-BATCH 영향 분석:**

- BATCH-N 적재 결정 → 24시간 후 BATCH-(N+1) 적재 시작
- (B) 7일 Rollback = BATCH-N+1 적재 후 BATCH-N 결정 Rollback?
- → Cross-BATCH 회귀 영향 추적 매우 어려움
- (A) 24시간은 다음 BATCH 진입 전 안전

**HACKER 의 구현 단순성:**

- (C) 즉시 확정 = 코드 가장 단순
- (A) 24시간 = 중간 복잡도
- (B) 7일 = 가장 복잡

**GHOST 의 storage 분석:**

- 모든 결정에 revert_event 저장
- (A) 24시간 = 최근 24시간 결정만 별도 partition
- (B) 7일 = 1주일 결정 별도 partition + cleanup cron
- D1 storage 미미 (~10KB/일)

**BREAKER 의 잘못된 결정 비율:**

- AI 추천 95% 신뢰도 = 5% fail
- 진산님 직접 결정 = 더 낮은 fail rate (1~2%)
- 합산 = 결정 100건당 1~5건 잘못
- → Rollback 안전망 필수 (C 옵션 반대)

### 메피스토펠레스의 함정

```
함정 1 (A 의 미묘한 위험):
24시간 = 진산님이 매일 24시간 내 검토 의무
→ 휴가 중 (3일+) 결정 검토 불가
→ 휴가 후 잘못된 결정 발견해도 이미 확정

해결: "확정" 의 자동 트리거를 24시간이 아닌 "다음 BATCH 적재 직전" 으로 변경.
즉, 다음 BATCH 진입까지는 무한 Rollback 가능.
```

```
함정 2 (B 의 명백한 위험):
7일 = BATCH-N 결정 Rollback 시점에 BATCH-(N+1) 이미 적재됨
→ Rollback 시 BATCH-(N+1) 도 영향 받는지 자동 분석 필요
→ CBIV Stage 5 의 회귀 Golden 재실행 (역방향)
→ 매우 복잡, 실패 risk

7일 = "안전 우선" 처럼 보이나 실제로는 더 위험.
```

```
함정 3 (C 의 진짜 위험):
즉시 확정 = 잘못된 결정 영구
→ 진산님이 결정에 더 신중해짐 (좋음)
→ 그러나 검수 시간 증가 (5초 → 15초)
→ alert fatigue 가속화 (나쁨)

C 의 단순성 vs B/A 의 안전성 trade-off.
1인 검수자 시나리오에서는 (A) 가 균형.
```

### 페르소나 합의 권고

> **권고: (A) 24시간 — 단, 함정 1 의 해결안 적용**
> **변형 권고:** "**24시간 또는 다음 BATCH 적재 직전, 둘 중 더 빠른 시점까지 Rollback 가능**"
> **추가:**
>
> - 큐 3 (CBIV 차단 정정) 의 Auto-Fix/Manual Fix 결정 = **1시간 내** Rollback (긴급)
> - 큐 1/2 의 결정 = **24시간 또는 다음 BATCH 진입 전** (균형)

**근거:**

- (B) 7일 = Cross-BATCH 영향 추적 불가능 (ARCHITECT 강력 반대)
- (C) 즉시 = 안전망 0 (BREAKER + SENTINEL 강력 반대)
- (A) 24시간 + 함정 1 해결 = 휴가 중 안전 + Cross-BATCH 안전

## 결정 10: 단축키 학습 (tutorial/사이드바/? 키)

### 옵션 분석

| 옵션                            | 학습 방식            | 영향                         |
| ------------------------------- | -------------------- | ---------------------------- |
| (A) 첫 진입 시 tutorial overlay | 1회 학습, 그 후 자율 | 학습 곡선 ↓                  |
| (B) 영구 사이드바               | 항상 표시            | 화면 공간 ↓, 자율 학습 ↓     |
| (C) ? 키 누를 때만 (vim 스타일) | 자율 학습            | 학습 곡선 ↑, 익숙해지면 best |

### DEV COVEN 분석

**ADVOCATE 의 학습 곡선:**

- (A) tutorial overlay = 신규 사용자 친화
- 진산님은 1회만 학습하면 됨 (1인 검수자)
- (C) ? 키 = 익숙해지기 전까지 매번 도움말 호출
- (B) 사이드바 = 화면 공간 낭비 (검수 화면 좁아짐)

**HACKER 의 vim 사용자 경험:**

- vim 사용자: ? 키 자연스러움
- 비-vim 사용자: 사이드바 또는 tutorial 필요
- 진산님이 vim 사용자인지 알 수 없음

**MEPHISTO 의 1회성 학습:**

- 진산님 단독 사용 = 1회 학습 후 평생 사용
- → tutorial (A) 가 최적
- 사이드바 (B) 는 영구 학습자에게 어울림 (대규모 팀)

**GHOST 의 화면 공간:**

- 사이드바 (B) = ~200px 영구 점유
- 검수 화면 본질 = side-by-side diff (넓은 공간 필요)
- 사이드바 = diff 가독성 저하

**ORACLE 의 사용자 경험 비전:**

- 검수 UI 본질 = "5초 결정"
- 단축키 = 5초 결정의 도구
- 도구 학습은 1회 + 자율 (A + C 결합)

### 메피스토펠레스의 함정

```
함정 1 (A 의 미묘한 위험):
첫 진입 tutorial = 1회 후 잊혀짐
→ 6개월 후 단축키 잊어버림
→ 다시 학습 어려움 (tutorial 재실행 기능 없으면)

해결: ? 키 hover 또는 "Help" 메뉴로 tutorial 재실행 가능.
```

```
함정 2 (B 의 명백한 함정):
사이드바 영구 표시 = 항상 보이지만 항상 무시됨
(브라우저 광고와 같은 banner blindness)
→ 학습 효과 0
→ 화면 공간만 낭비
```

```
함정 3 (C 의 미묘한 위험):
? 키 vim 스타일 = vim 사용자에게는 best
그러나 비-vim 사용자에게는 "? 키 = 도움말" 인식 부재
→ 단축키 학습 안 됨 → 마우스만 사용 → UI 본질 (5초 결정) 깨짐
```

### 페르소나 합의 권고

> **권고: (A) 첫 진입 시 tutorial overlay + (C) ? 키 hover (결합)**
> **단,** 아래 조건 동반:
>
> - **첫 진입 = tutorial overlay 자동 표시** (skip 가능)
> - **? 키 누를 때 = 단축키 cheat sheet overlay** (언제든 호출)
> - **"Help" 메뉴에서 tutorial 재실행 가능** (잊어버린 경우)
> - **사이드바 (B) 는 미도입** (화면 공간 + banner blindness)

**근거:**

- (A) 단독 = 잊어버림 risk
- (C) 단독 = vim 비-사용자 부적합
- (A) + (C) 결합 = 학습 + 자율 + 재학습 모두 가능

**구현 명세:**
