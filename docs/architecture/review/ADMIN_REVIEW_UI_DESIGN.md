# Admin Review UI 설계 — 검수자 피로감 제로 아키텍처

> **답변 대상:** "CBIV 가 뿜어내는 '의미 중복(Stage 2)'과 '출제영역 정합성 경고(Stage 6)'를 인간 검수자가 피로감 없이 직관적으로 판단하고 처리(Merge/Reject/Keep Both)할 수 있도록, Admin CMS(`admin-web`) 내 검수 UI의 플로우는 어떠한 형태로 구현할 계획이십니까?"
>
> **답변:** 3개 검수 큐 + One-click Action + AI 추천 + Keyboard Navigation = 검수 시간 90% 단축
>
> **위치:** [재정립안 v2.1 PATCH](./CONTENT_BUILD_ENGINE_REDESIGN_v2_1_PATCH.md) §8 의 본격 응답
> **상위:** [ADMIN_ARCHITECTURE_SUPPLEMENT.md](./ADMIN_ARCHITECTURE_SUPPLEMENT.md)

## 0. 본 문서의 본질 (ADVOCATE 의 선언)

> "검수자가 피로하면 시스템이 무너진다.
> CBIV 가 자동화의 99% 를 담당해도, 마지막 1% (인간 결정) 가 병목이면 전체가 멈춘다.
> 그 1% 를 **5초 미만** 에 처리할 수 있도록 만든다. 그것이 본 문서의 임무."

검수 UI 의 적은 **alert fatigue** (경고 피로). 진산님이 100건의 flag 를 받으면:

- 1~10건: 신중히 검토
- 11~30건: 패턴 인식 시작
- 31~50건: 빠른 판단 시도
- 51건+: **모두 무시 또는 일괄 reject** ← 시스템 사망

본 UI 의 목적: 100건이 와도 5초/건 = 8분 내 처리 가능한 환경 구축.

## 1. 3개 검수 큐 정의

CBIV 의 출력은 3가지 카테고리로 분기:

```
┌─────────────────────────────────────────────────────────────────┐
│  CBIV 6단계 자동 검증                                            │
└────────────────────────────┬────────────────────────────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ 큐 1:            │  │ 큐 2:            │  │ 큐 3:            │
│ 의미 중복 검수   │  │ 출제영역 경고    │  │ CBIV 차단 정정   │
│                 │  │                 │  │                 │
│ Stage 2 출력     │  │ Stage 6 출력     │  │ Stage 1/3/4/5    │
│                 │  │                 │  │ 실패            │
│ 액션: Merge /    │  │ 액션: Approve / │  │ 액션:           │
│       Reject /  │  │      Reassign / │  │   Investigate / │
│       Keep Both │  │      Investigate│  │   Auto-Fix /    │
│                 │  │                 │  │   Manual Fix    │
│                 │  │                 │  │                 │
│ 빈도: 중         │  │ 빈도: 저         │  │ 빈도: 저 (희망) │
│ 임계: 비차단     │  │ 임계: 비차단     │  │ 임계: 차단됨     │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

### 1.1 큐 1: 의미 중복 검수 큐 (가장 빈번)

**상황:** CBIV Stage 2 가 신규 노드를 기존 노드와 코사인 유사도 임계값 초과로 flag.

**예시:**

> 신규 노드 `F-30 (밭작물 손해정도비율 산식)` 이 기존 노드 `F-04 (사과 손해정도비율 산식)` 와 코사인 유사도 0.96 (FORMULA 임계값 0.95 초과).

**검수자 결정:**

- ✅ **Merge**: 둘이 같은 노드 → 하나로 통합 (신규 폐기, 기존 사용)
- ❌ **Reject**: 신규 노드가 잘못 생성됨 → 폐기 + 진산님 정정 의뢰
- 🔀 **Keep Both**: 둘 다 다른 노드 → 임계값 false positive (작물 다름) → 둘 다 유지

### 1.2 큐 2: 출제영역 정합성 경고 큐

**상황:** CBIV Stage 6 가 신규 노드의 `exam_scope` 메타가 BATCH 정의 영역과 불일치 감지.

**예시:**

> BATCH-1 (적과전 종합위험) 적재 시 노드 `INV-NNN (벼 침수율 조사)` 생성됨. 그러나 침수율 조사는 BATCH-3 (논작물) 영역.

**검수자 결정:**

- ✅ **Approve as Cross-Reference**: 정상적인 cross-domain REFERENCES → 그대로 적재
- 🔄 **Reassign**: 잘못된 영역 분류 → 올바른 BATCH 로 이관
- 🔍 **Investigate**: 판단 어려움 → 보류, 추가 컨텍스트 검토

### 1.3 큐 3: CBIV 차단 정정 큐 (긴급)

**상황:** CBIV Stage 1/3/4/5 가 BATCH 적재를 자동 차단함.

**예시:**

> BATCH-4 (밭작물) 적재 시도 → Stage 5 (회귀 Golden Test) 가 BATCH-R1 (26년 개정) 의 Golden Test "손해정도비율 = 0.10" 을 깨뜨림. 원인: F-30 이 임계값 0.20 하드코딩.

**검수자 결정:**

- 🔍 **Investigate**: root-cause-analyzer 의 분석 + 원본 자료 검토
- 🤖 **Auto-Fix**: AI 가 제안한 정정 (예: F-30 → CONST-901 참조) 채택
- 🛠️ **Manual Fix**: 진산님이 직접 정정안 작성

## 2. UI 메타 원칙 (ADVOCATE 의 헌장)

### 원칙 1: One-click Action (5초 결정)

검수 결정은 **클릭 1번** 으로 끝나야 함. 다음 단계 (Merge 시 어느 노드를 keep 할지 등) 는 **default + override** 패턴.

```
[Merge 클릭] → 자동: "기존 노드 keep, 신규 폐기, 신규의 page_ref 만 기존에 추가"
              → 검수자가 다른 정책 원하면 "Advanced" 토글로 변경
```

### 원칙 2: Side-by-side Diff

두 노드 비교는 **시각적 좌우 배치 + 차이 highlight**:

```
┌─────────────────────────┬─────────────────────────┐
│ 기존: F-04              │ 신규: F-30              │
├─────────────────────────┼─────────────────────────┤
│ name: "사과 손해정도비율"│ name: "밭작물 손해정도..."│
│ formula: 임계값 ★0.10★  │ formula: 임계값 ★0.20★  │
│ page_ref: 525           │ page_ref: 543           │
│ valid_from: 2026-01-01  │ valid_from: 2026-01-01  │
│ truth_weight: 8         │ truth_weight: 8         │
└─────────────────────────┴─────────────────────────┘
                ↑ 차이점 자동 highlight
```

### 원칙 3: AI 사전 분석 + 추천

Claude 가 **결정을 추천** + **근거** 제시:

```
🤖 AI 분석:
   "이 두 노드는 다른 작물 (사과 vs 밭작물) 의 산식입니다.
    같은 임계값을 사용하나 적용 영역이 다릅니다.
    추천: Keep Both (95% 신뢰도)
    근거:
    - name 의 'crop_type' 부분이 명확히 다름
    - page_ref 가 다른 섹션 (525 vs 543)
    - 손해평가사 도메인에서 작물별 산식은 별개"

[추천 채택: Keep Both]  [Override]
```

### 원칙 4: Keyboard Navigation

마우스 없이 vim 스타일 단축키로 처리:

```
J / K     ─ 다음 / 이전 항목
M         ─ Merge
R         ─ Reject
B         ─ Keep Both
A         ─ Approve (큐 2/3)
I         ─ Investigate
?         ─ AI 추천 채택
1-9       ─ 빠른 액션 단축키
Cmd+Enter ─ 일괄 처리 모드 진입
ESC       ─ 액션 취소
```

### 원칙 5: 일괄 처리 (Bulk Action)

같은 패턴의 flag 는 **한 번에 처리**:

```
"BATCH-1 의 사과 산식 5건이 BATCH-2 의 배 산식 5건과 0.96 유사도로 flag 됨.
 모두 Keep Both? 5건 모두 적용?"
[YES — 5건 일괄 Keep Both]  [개별 검토]
```

### 원칙 6: 검수 진행률 시각화

시스템적 동기 부여:

```
┌─────────────────────────────────────┐
│ 오늘의 검수 진행률                    │
│ ▓▓▓▓▓▓▓▓░░ 85건 / 100건 (85%)        │
│ 평균 시간: 4.2초/건                  │
│ 예상 완료: 13분                      │
│                                      │
│ 이번 주 누적: 412건 처리              │
│ AI 추천 채택률: 78%                  │
└─────────────────────────────────────┘
```

## 4. 의사결정 지원 도구

### 4.1 Side-by-side Diff Viewer

```typescript
// apps/admin-web/src/components/review/DiffViewer.tsx
interface DiffViewerProps {
  existing: KnowledgeNode;
  incoming: KnowledgeNode;
  highlightDifferences: boolean;
}

// 자동 highlight 알고리즘:
// 1. 같은 필드 비교 (id, name, formula, ...)
// 2. 다른 값 → ★...★ wrap + 노란 배경
```

## 6. 일괄 처리 (Bulk Action) 모드

### 6.1 자동 패턴 감지

CBIV 결과를 분석해서 **유사 패턴** 자동 그룹핑:

```
[CBIV 결과]
- F-04 ↔ F-30 (FORMULA, 0.96)  ┐
- F-05 ↔ F-31 (FORMULA, 0.95)  ├─ "BATCH-4 산식 vs BATCH-1 산식"
- F-06 ↔ F-32 (FORMULA, 0.97)  │  패턴 5건 일괄 처리 가능
- F-07 ↔ F-33 (FORMULA, 0.96)  │
- F-08 ↔ F-34 (FORMULA, 0.95)  ┘
```

### 6.2 일괄 액션 UI

```
═══════════════════════════════════════════════════════════════════════
  일괄 처리 모드 — 5건 (BATCH-4 산식 패턴)
═══════════════════════════════════════════════════════════════════════

  감지된 패턴:
  ┌─────────────────────────────────────────────────────────────────┐
  │ "BATCH-4 의 밭작물 산식들이 BATCH-1 의 적과전 산식들과              │
  │  0.95+ 유사도로 flag 됨. 작물 카테고리만 다름."                    │
  └─────────────────────────────────────────────────────────────────┘

  영향 항목 (5건):
  ✓ F-30 ↔ F-04 (밭작물 vs 사과)
  ✓ F-31 ↔ F-05 (밭작물 vs 배)
  ✓ F-32 ↔ F-06 (밭작물 vs 단감)
  ✓ F-33 ↔ F-07 (밭작물 vs 떫은감)
  ✓ F-34 ↔ F-08 (밭작물 vs 모과)

  🤖 AI 일괄 추천: Keep Both (5건 모두, 95% 신뢰)
  근거: 작물 카테고리만 다른 별개 산식 (false positive 패턴)

  ┌─────────────────────────────────────────────────────────────────┐
  │ 일괄 액션:                                                       │
  │  [B] ✅ 5건 모두 Keep Both                                        │
  │  [✓] 개별 검토 — 1건씩 결정                                        │
  │  [✗] 일괄 모드 취소                                               │
  └─────────────────────────────────────────────────────────────────┘
```

### 6.3 일괄 처리 안전 장치

- **반드시 같은 패턴**: 다른 카테고리 섞이면 자동 분리
- **일괄 처리 시 5초 카운트다운**: 잘못 누르면 ESC 로 취소 가능
- **일괄 처리 후 audit log**: "2026-04-26 15:30 — 5건 일괄 Keep Both" 기록

## 12. DEV COVEN 페르소나별 사인-오프 (검수 UI)

> **MEPHISTO**: "CBIV 의 자동화는 99%, 검수 UI 가 마지막 1%. 그 1% 가 무너지면 99% 가 의미 없다."

> **ADVOCATE**: "검수자 (진산님) 가 인간이라는 사실을 시스템 설계 한가운데 두었다. 그것이 본 UI 의 전부."

> **HACKER**: "8시간 = 28 task. TDD 사이클 28회. 평이한 React/Astro 작업."

> **BREAKER**: "Rollback 24시간 + audit log = 잘못된 결정으로부터 시스템 보호. 가장 critical 한 안전망."

> **ARCHITECT**: "API 분리 + 컴포넌트 분리 = 유지보수 가능한 구조. 새 큐 추가는 패턴 복제만."

> **GHOST**: "키보드 navigation = 마우스 의존성 0. 운영 환경에서 빠른 결정 가능."

> **SENTINEL**: "Audit log + 권한 분리 (rollback 은 결정자만) = 보안 영역 보강."

> **ORACLE**: "북극성 = 신뢰성·정확성. 검수자가 피로해서 잘못된 결정을 하면 신뢰성 0. 본 UI 가 그것을 막는다."
