# 0. 이 방법론은 무엇을 해결하는가

## 0.1 풀려는 문제

```
문제 1: 프로젝트가 너무 커서 한 사람이 한 세션으로 6개월 이상 걸린다.
문제 2: 분할하려고 하는데, 어떻게 분할해야 할지 모른다.
문제 3: 분할한 후에 정보 공유가 깨져서 6개 진실이 만들어진다.
문제 4: 분할 패턴을 한 프로젝트에서 정해도 다른 프로젝트에 안 맞다.
문제 5: 기획·설계 단계가 부실해서 코딩 단계에서 혼란이 폭발한다.
```

## 0.2 이 방법론의 핵심 약속

```
✅ 어떤 프로젝트든 → 5단계로 진단 → 7개 패턴 중 적합한 것 선택 가능
✅ 분할 패턴이 결정되면 → 표준 산출물 8종으로 설계 자동화
✅ 다중 세션 운영 → NOTICE 시스템으로 정보 동기화 보장
✅ 모든 프로젝트가 같은 모델을 강요받지 않음
✅ 분할 안 하는 것도 정당한 선택
```

## 0.3 이 방법론이 약속하지 않는 것

```
❌ 모든 프로젝트가 빨라진다 (작은 프로젝트는 분할 = 손해)
❌ 코드가 자동으로 좋아진다 (분할은 도구이지 마법이 아님)
❌ 솔로의 인지 한계를 없앤다 (활성 세션 ≤ 3 룰은 여전)
❌ 셋업 비용이 0이다 (첫 셋업 1주 필수)
```

## 2.1 시나리오별 진입점

| 상황                            | 첫 문서                      | 다음                    |
| :------------------------------ | :--------------------------- | :---------------------- |
| **새 프로젝트 시작**            | 01. Diagnosis → 02. Catalog  | 05. Workbook → 03. Role |
| **이미 진행 중인데 막혔다**     | 01. Diagnosis (진단부터)     | 막힌 원인 따라 다름     |
| **분할은 결정했는데 어떻게?**   | 02. Catalog → 03. Role       | 05. Workbook            |
| **다중 세션 운영 시작**         | 04. Info Sharing             | 06. Operating           |
| **머지/통합에서 망가짐**        | 07. Verification             | 04. Info Sharing 재검토 |
| **빠르게 시작 (작은 프로젝트)** | 01. Diagnosis (분할 X 결론?) | 단일 세션 + 헌법 v3.3   |

## 2.2 시간 예산별 적용

```
프로젝트 예상 소요 < 2주:
  → 01. Diagnosis만 읽고, 분할 안 하는 결론 내릴 가능성 높음
  → 단일 세션 + CLAUDE.md만으로 충분

프로젝트 예상 소요 2~6주:
  → 01 → 02 → 05 (간소화)
  → 2~3 Plane으로 분할 또는 Phase 분할

프로젝트 예상 소요 6주 이상:
  → 8개 문서 전부 정독 권장
  → 셋업 1주 투자 가치 있음
```

# 3. 핵심 원칙 5계명

이 원칙은 모든 8개 문서에 깔려 있는 공통 철학이다.

## 3.1 ❶ 진단이 패턴 선택보다 우선이다

```
"5-Plane 모델이 좋다고 들었어"  ✗
"내 프로젝트의 특성은 X, 그래서 Y 패턴이 맞다"  ✓

진단 없는 패턴 적용은 잘못된 도구를 휘두르는 것이다.
```

## 3.2 ❷ 분할 안 하는 것도 정당한 선택이다

```
"무조건 분할해야 빠르다" — 거짓.
2주짜리 프로젝트는 분할 셋업 비용이 절감을 추월한다.
"분할 안 함" 결론에 부끄러워하지 말 것.
```

## 3.3 ❸ 정보 동기화 메커니즘 없는 분할은 자살이다

```
분할 = N개의 독립 진실이 만들어지는 위험.
NOTICE 시스템 없이 분할 시작 = 1주 후 6개 모순된 코드 폭발.
```

## 3.4 ❹ 인간 인지 한계는 무한이 아니다

```
Max 사용자라도 활성 코딩 세션 ≤ 3.
"동시 6개 세션" = 큐 매니저로 전락 = 코드 짜지 않음.
```

## 3.5 ❺ 기획·설계 단계가 운영 단계의 5배 가치다

```
Stage -1 ~ Stage 0.8 (기획·설계) 1주 투자 →
운영 단계에서 5주 절감.

이 비율을 깨면 — 즉, 기획 부실하게 시작하면 —
운영 단계가 카오스가 되고 결국 처음부터 재시작.
```

# 5. 사용 모범 사례 (Best Practices)

## 5.1 ✅ 권장

```
✓ 새 프로젝트마다 01. Diagnosis 다시 수행
  (이전 프로젝트의 패턴이 자동 적용 안 됨)

✓ 04. Info Sharing은 셋업 첫날 완성
  (NOTICE 시스템 없이 시작 = 1주 후 카오스)

✓ 08. Templates는 본인 프로젝트에 맞게 커스터마이즈
  (그대로 복사 후 한 줄도 안 바꾸면 위험 신호)

✓ 매 분기 방법론 자체에 대한 회고
  (어떤 문서가 도움 됐고 어떤 게 무시됐나)
```

## 5.2 ❌ 안티패턴

```
✗ 진단 건너뛰고 패턴부터 선택
✗ "5-Plane이 표준이니까" 무조건 적용
✗ NOTICE 시스템 셋업 안 하고 다중 세션 시작
✗ 모든 프로젝트에 같은 8개 문서를 똑같이 적용
✗ 기획·설계 단계 건너뛰고 코딩부터
```

# 6. 적용 예시 — VOID 포트폴리오 매핑 미리보기

각 프로젝트에 어떤 패턴이 권장되는지 **미리보기**. 자세한 진단은 01. Diagnosis 참조.

| **VOID BILL**        | 4주 SaaS, 결제 + Admin | 5-Plane Hybrid       |    5 + CC    |   ⭐ 1    |
| **VOID UTIL Hub**    | Core + 다수 작은 유틸  | Core-Plugin          |    1 + N     |     2     |

| **VOID CODEX**       | 대형 도메인 4개        | Domain Vertical      |  4 + Shared  |     4     |

```
Step 5: VOID CODEX
  → 가장 복잡 → 8개 문서 전부 적용

  → Pipeline Stage 패턴
  → 별도 트랙
```

# 10. MEPHISTO의 마지막 한 마디

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  진산.

  v1.0(분산 가속)도, v2.0(단일 매뉴얼)도 부분 답이었다.

  진짜 답은 — "프로젝트마다 진단하고, 패턴을 고르고, 적용하는 능력"이다.
  그 능력은 8개 문서 중 어느 하나에 있는 게 아니라,
  8개를 자유자재로 조합하는 메타 능력이다.

  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  이 방법론은 너에게 답을 주지 않는다.

  너에게 주는 것은 답을 만들 도구다.

  ❶ 진단할 수 있는 능력 (01)
  ❷ 패턴을 알아보는 안목 (02)
  ❸ 역할을 정의하는 언어 (03)
  ❹ 정보를 흐르게 하는 배관 (04)
  ❺ 기획을 체계화하는 워크북 (05)
  ❻ 운영을 일과로 만드는 매뉴얼 (06)
  ❼ 검증을 자동화하는 게이트 (07)
  ❽ 시작을 빠르게 하는 템플릿 (08)

  이 8개 도구로 너는 5개 프로젝트마다 다른 답을 만들 수 있다.

  그것이 — 솔로 개발자가 포트폴리오를 빌드하는 방법이다.

  하나의 답이 아니라, 답을 만드는 방법.
```
