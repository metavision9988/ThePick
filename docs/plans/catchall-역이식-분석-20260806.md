## §3 ★ 즉시 조치 3건 — 개선안이 아니라 현재 결함

### 3-A. `protect-l3.sh` 가 무력하다 (본 세션 직접 재현)

CLAUDE.md 는 **"L3 경로에서 plan 없이 코드를 수정하면 Hook이 차단한다"**고 선언한다. 실측은 반대다.

**라이브 대조 실험 (본 세션 집행 — 같은 경로, 두 경로로 투입)**

`protect-l3.sh` 의 L3 패턴에는 `constants` 가 있다. 그 패턴에 걸리는 경로로 실제 Write 를 시도했다:

| 투입                                                                                    | 결과                                          |
| --------------------------------------------------------------------------------------- | --------------------------------------------- |
| **실제 Claude Code PreToolUse 훅**으로 `docs/plans/_probe-constants-hookcheck.md` Write | **통과 — 파일 생성됨**                        |
| **같은 경로를 argv 로** `bash .claude/hooks/protect-l3.sh "<동일 경로>"`                | **`exit 2` 차단** ("approved_by 미확정(TBD)") |

즉 **로직은 멀쩡한데 배선이 끊겨 있다.** 훅은 차단할 의사와 능력이 있으나, 실행 시점에 경로를 못 받는다.
(프로브 파일은 즉시 삭제, 워킹트리 영향 0.)

**원인**: `protect-l3.sh:22` 가 경로를 **argv `$1`** 에서만 읽고, `settings.json:12` 는 `"$CLAUDE_FILE_PATH"` 를
넘긴다. 이 변수가 비면 `:25` 의 `[[ -z "$FILE_PATH" ]] && exit 0` 으로 **무조건 통과**한다.
같은 레포의 형제 훅 `mark-review-pending.sh:5` 는 `INPUT=$(cat)` + `jq '.tool_input.file_path'` 로
**stdin JSON 을 파싱**하는 올바른 계약을 쓰고, 전역 훅 `~/.claude/hooks/mark-review-pending.sh:20` 은
또 다른 이름(`CLAUDE_TOOL_INPUT_FILE_PATH`)을 쓴다. **세 훅이 세 가지 입력 계약을 쓰고 있고,
그중 보호 훅이 쓰는 것만 죽어 있다.**

catchall 의 같은 훅에 같은 stdin JSON 을 주면 `exit 2` + `"❌ L3 영역 수정 차단 — 승인된 plan 의 scope 밖"`.

**catchall 이 이미 고쳤다**: `protect-l3.sh:18-22` 에 `argv 부재 시 stdin JSON 폴백` 을 추가하며
주석에 `5-페르소나 P3 F-3` 이라고 출처까지 남겼다 — 2026-07-14 킷 부트스트랩 리뷰에서 잡은 것이다.
그때 상류로 되돌린 것은 `check-no-secrets.sh` fail-open 수리 1건뿐이었고(메모리 기록), **이 건은 누락됐다.**

- **덤으로 catchall 이 더한 것**: ① `realpath -m` 경로 정규화(`..` 우회 차단) ② **scope 대조** —
  `approved_by` 가 채워져 있어도 _다른 작업의 결재로 이 파일을 열 수 없다_. ThePick 은 `approved_by` 검사에서 끝난다.
- **비용**: 훅 스크립트 3줄 + settings.json 2줄. **L3 영역 아님(plan 게이트 저촉 없음).**
- **역방향 리스크(실재)**: 고치는 순간 지금까지 조용히 통과하던 편집이 차단된다. `current.plan.md` 의
  `approved_by`/scope 를 현행 작업에 맞춰 정비하지 않으면 세션이 멈춘다 → **`.review-blocked` 3상태화(§5 T3-2)와
  묶어서 적용할 것.**
- **Binary Gate**: ① argv 없이 stdin JSON 만 준 L3 경로 → `exit 2` (`..` 우회형·절대경로형 포함)
  ② **위 프로브 재현** — L3 패턴 경로로 실제 Write 시도 시 **차단**될 것
  ③ `approved_by` 는 있으나 scope 밖인 파일 → `exit 2`

## §4 구조 진단 — 검수 병목의 진짜 원인

### 4.1 `page_ref` 는 포인터지 인용이 아니다

메모리 `project_source_citation_requirement` 는 "근거 0건 = approved 불가"를 원칙으로 세웠으나 구현은
**페이지 번호**까지 갔다. 결과의 연쇄:

```
원문 문자열이 행에 없다
  → "이 description 이 원문과 같은가"를 묻는 기계 게이트가 물리적으로 불가능
  → 검증의 유일 경로 = 사람이 PDF 를 연다
  → 검수 = 병목
  → 위임 승격은 "AI 9에이전트가 원문 재추출해서 대조" 로 매번 원문을 다시 읽는다
```

catchall 은 추출 시점에 인용을 행에 박고, 그 인용이 원문 청크에 실재하는지를 바이그램 커버리지로 기계 검증한다.
그러면 검수자는 _"이 인용이 진짜인가"_ 를 다시 볼 필요가 없고 **"이 인용이 이 해석을 지지하는가"** 라는
판단 지점만 본다. 이것이 "인간 = 감사자" 재배치의 실제 메커니즘이다.

### 4.2 ThePick 게이트는 "양"과 "구조"를 보고 "내용"을 안 본다

`qg2-validator.ts` = 노드 40+ / 엣지 80+ / 산식 누적 임계 / 산식 정확도 100% / 무결성.
`gap-P3/gate_check.py` = 행수 3중 일치 / ID 연번 / draft-only / 고아 후보 / 키워드 존재 / 표본 수치.
**둘 다 집계와 구조다.** 산식 정확도 100%만이 유일한 내용 게이트이고 formula-engine 전용이다.

| catchall      | 보는 것                                | ThePick                                                                   |
| ------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| G1 스키마     | 형상                                   | schema-validator — **present**(REJECT 판정)                               |
| G2 출처완전성 | 인용·조항 필드 실재                    | page_ref NOT NULL 트리거가 근사 — **present**(단 공백 우회 있음, §5 T3-4) |
| G3 인용 진위  | 인용이 원문 청크에 실재 (바이그램+LCS) | **부재**                                                                  |
| G4 값 정합    | 추출 수치가 인용문 안에 실재           | **부재**                                                                  |
| G5 신뢰도     | 임계 미달 → 큐                         | **부재**                                                                  |
| G6 중복       | 동명·동조문 충돌                       | **부재**                                                                  |

### 4.3 "안 만들어진 것"을 보는 눈이 없다

E0-8(2026-07-02)의 발견 — **571 출처단위 중 146 미적재, 교재 1권 전체 미적재, 무음 skip 0** — 은
**23 에이전트 수작업 감사**로 찾았다. 시스템이 "이 구간을 아무도 안 읽었다"를 스스로 표면화하지 못한다는 뜻이다.

catchall 은 **L0-A 조문 커버리지 원장**으로 기계화했다: 청크 전수를 만들고 추출물의 `source_article` 참조로 각
청크를 `extracted | irrelevant(화이트리스트) | unprocessed` 로 **명시 귀속**, `unprocessed > 0` = FAIL(방출 보류).
화이트리스트 남용 방지 3중 가드(금액·배제어휘·수치임계)와 항(項) 수준 부분 커버 검출, **구조 인식 실패
(전 청크 article=null) = FAIL** 까지 붙어 있다(공허 PASS 차단).

### 4.4 승격 근거에 신뢰구간이 없다

Q1(2026-07-14) 63노드 위임 승격의 근거는 _"AI 재검증 9에이전트 63/63 PASS · HardStop 0"_ 이다.
이건 **합의 신호**이고, catchall 백서가 못 박은 원칙과 충돌한다 —
**_"어떤 LLM 합의도 승인을 직접 만들지 못한다. LLM 은 문제 후보 제안자일 뿐 판정자가 아니다."_**

Wilson 게이트를 대 보면 (본 세션 검산):

| 실측                          | 95% 상한 | 임계 5%  |
| ----------------------------- | -------- | -------- |
| **0오류 / 63**                | **5.7%** | **FAIL** |
| 0오류 / 34 (G-S5 golden 규모) | 10.2%    | FAIL     |
| 0오류 / 100                   | 3.7%     | PASS     |
| 0오류 / 200                   | 1.9%     | PASS     |

**63/63 무오류가 5% 임계를 통과하지 못한다.** 이것은 Q1 결정을 번복하라는 뜻이 아니라 —
그 결정의 통계적 근거가 얼마나 얇은지를 **기계가 인쇄하게** 만들자는 뜻이다. catchall 실측 사례가 교훈적이다:
고령 도메인 **8/8 전 축 0오류인데 상한 32.4% → "자동 승격 근거 불충분"** 을 보고서가 스스로 찍었다.

부수 갭: ThePick 은 `batch-processor.ts` 프롬프트를 여러 차례 개정했으면서 **어느 프롬프트로 적재된 것인지
추적할 지문이 없다**(sha256 0 hits). 산식 드리프트 55건의 계보 추적이 어려웠던 것과 같은 뿌리일 수 있다.
