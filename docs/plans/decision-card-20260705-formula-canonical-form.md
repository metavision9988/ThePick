## §1 핵심 발견 — "단일 canonical form은 구조적으로 불가능"

수식은 4개 계층을 통과한다. **각 계층의 하드 제약이 서로 다른 표기형을 강제**한다:

| 계층                            | 하드 제약 (실측)                                                                                                                                                                                          | 강제 표기형                         | 증거                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------- |
| **① 계산 (formula-engine AST)** | math.js `internalParse`가 파싱하는 것만 계산. 변수 = `/^[a-z][a-z0-9_]*$/`(라틴 소문자 snake_case), 함수 = 화이트리스트 16종, ASCII 연산자 `* / + -`. 유니코드(× ÷ √)·그리스·대문자·LaTeX 전부 파싱 실패. | **ASCII math.js infix** (회피 불가) | `sandbox.ts:45-66`, `ast-parser.ts:45-76`       |
| **② 표시 (MC UI 렌더)**         | 수학 조판기 **전무**(KaTeX/MathJax/MathML 0건). 전 콘텐츠 = 평문 JSX(auto-escape). `dangerouslySetInnerHTML` 0.                                                                                           | 저장 문자열 그대로(현재는 평문만)   | `QuestionCard.tsx:272`, grep katex/mathjax = 0  |
| **③ 임베딩 (bge-m3 검색)**      | `@cf/baai/bge-m3` 1024d 고정. 입력 = node `name+"\n"+description` verbatim(정규화 0, **equation 필드 미포함**). 저장 바이트열이 그대로 토큰화.                                                            | 검색 최적형 (**미측정 = S9**)       | `vectorize/routes.ts:355`, `upserter.ts:34,128` |
| **④ 도면 (S10 회로도)**         | lcapy+schemdraw 빌드타임 → 정적 SVG+JSON, 런타임은 **KaTeX 렌더 전제**(풀이단계 수식).                                                                                                                    | LaTeX (파이프라인 전제)             | `EXTERNAL_ELECTRICAL_EXPANSION_ANALYSIS:22-24`  |

**결론**: 계산층(①)은 **무조건 ASCII math.js**를 요구하므로, 어떤 결정을 내려도 "표시·임베딩과 별개의 계산용 ASCII 표현"은 항상 필요하다. → **"하나의 표준형으로 4층 커버"는 원천 불가능.** 스키마가 이미 이 이원성을 반영: `formulas.equation_template`(ASCII, NOT NULL) + `equation_display`(표시용, nullable) 2컬럼 실재(`schema.ts:264-283`).

**즉 플레이북의 3안(①유니코드평문 / ②LaTeX+KaTeX / ③하이브리드)은 두 직교 축(계산형 vs 표시형)을 혼동한 프레이밍이다. ③ 하이브리드는 "선택지"가 아니라 엔진·스키마가 이미 강제한 골격이다.** (코드 `FormulaDefinition`은 이미 `equationTemplate`[ASCII] + `equationDisplay`[유니코드 필수 필드] 보유 — `types.ts:34-35`.)

## §2 결정의 재구성 — 3축 분리 (진짜 결정 대상)

"하이브리드냐"가 아니라, **하이브리드 골격 안에서 각 축의 표기형을 무엇으로 못박느냐**가 결정 대상:

| 축                                  | 무엇을 정하나                                                                | 후보                               | 제약                                                                                                |
| ----------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------- |
| **A. 계산형** (`equation_template`) | AST 파서 입력 표준                                                           | ASCII math.js infix (bare-expr)    | **사실상 강제** — 결정 여지 = 형식 규약(대입형 `P=` 금지·snake_case romanize 규칙)뿐                |
| **B. 표시형** (`equation_display`)  | 학습자에게 보이는 표기                                                       | ①유니코드 평문 / ②LaTeX 소스       | **본 카드 핵심 결정.** greenfield(0/157)                                                            |
| **C. 임베딩형** (검색 입력)         | bge-m3 입력(node `name+description`) 내 **수식 표기**(description 산문 삽입) | 정규화 유니코드 / LaTeX / romanize | **S9 미측정 → LOCK 금지**. ★입력에 equation 필드 미포함 → 표시형(B) 결정이 임베딩에 자동 커밋 안 됨 |

## §4 권고 (진산 결재 대상 — 확정 아님)

**권고: 하이브리드 골격(강제) + 표시형 = KaTeX-대응 렌더러 + "복잡식 LaTeX·단순식 평문" 저작 규약(손해평가 68식 grandfather) + 임베딩형 = S9 게이트 후 확정.** 3-form 명시 분리:

1. **축 A · 계산형 `equation_template` = ASCII math.js infix** (강제). 형식 규약 신설: **bare-expression만**(대입형 `P = L*(S/V)` 금지 — D1 F-152~157 혼재 실측), 변수 = 라틴 snake_case romanize(`Z·ω → z·omega`). ⚠️ **복소수 표기(크기/위상 분해)는 축 A 규약 자체** → romanize 락은 **D-1 복소수 방침 확정 후**(§5·§8 순서, M-2 정정).
2. **축 B · 표시형 = 렌더러가 LaTeX(KaTeX) 대응, 저작은 필요 시에만 LaTeX**:
   - **렌더러**: 전기 복소수·분수·적분·첨자 스택은 유니코드 평문으로 조판 불가 → **KaTeX 대응 렌더러가 사실상 필수**(2D 조판 사실 — 검색과 무관, S9 불요). 대가 = web 첫 수식 의존성(PWA 폰트 self-host + SW 캐시 = Cloudflare 단일 벤더 정합 OK).
   - **저작 규약**: 2D 조판이 필요한 식만 LaTeX(구분자 마킹), 단순식은 평문 유니코드. → **손해평가 68식(현행 유니코드 display, 작동 중)은 재저작 없이 유지**(C-1 반영), 전기 복잡식만 LaTeX 신규 저작. 표시형은 **데이터 규약**(코드 분기 아님 → Hard Rule 15 무관, M-1 정정).
3. **축 C · 임베딩형 = S9 실측 후 확정 (지금 LOCK 금지)**. 임베딩 입력 = node `name+description`(equation 필드 미포함) → **표시형 결정과 독립**. 잠정 = NFC 정규화 유니코드. bge-m3의 수식 표기별 hit-rate 전부 미측정(83.3%는 산문 전용, 이전 보장 0) → S9 spike(전기 파일럿 20~30문항) 후 락.

**두 대안 (진산 판단용 — 정직한 비용):**

- **①A 유니코드 평문 단독**: 손해평가 68식의 **현행 작동 구현체**(status quo, UI 비용 0). 단 전기 복소수·2D 조판 표현력 구조적 한계(가독성 천장). 손해평가 단독이면 최적이나 2호=전기 상황에서 렌더러 표현력 부족.
- **②B LaTeX 전 종목 공통 단독**: 표기 단일화·툴링 일관. **단 손해평가 68 유니코드 display를 전부 LaTeX로 재저작+검수(기능 이득 없는 비용)** + 단순식 LaTeX 오버헤드. 권고(하이브리드)는 이 재저작을 회피하면서 전기 LaTeX 표현력을 확보. **딜레마**: 단일 LaTeX(68 재저작) vs 복잡도별 저작(68 유지·표기 이종 수용) — 진산 결재 시 인지.

## §6 비가역성 · 타이밍

- **전기 D1은 지금이 최저비용 확정 시점**: `exams/전기` 스캐폴드·`migrations-v2/` 미존재, ELEC 산식 0건, 전기 `equation_display` 0 → **전기 표시 규약을 지금 못박으면 전기 D1 재적재 0**. 전기 첫 적재 후 변경 = 전량 SUPERSEDES.
- ⚠️ **손해평가 68식 비용 (C-1 정정)**: D1 `equation_display`는 0/157이나 **코드 레지스트리 `FormulaDefinition.equationDisplay`는 68식 전부 유니코드 평문으로 실재·작동**(필수 필드 `types.ts:35`, `batch1-definitions.ts:18·175·218`). "②B LaTeX 전 종목 공통" 채택 = 68식 재저작+검수(≠0). 권고(단순식 평문 grandfather)는 이 비용을 회피.
- **축 A 형식 규약(bare-expr·romanize)** 확정 = normalizer SHA-256 AST 해시 재산출 유발(드리프트 게이트) → D-3 동반 + **D-1 복소수 방침 선행**.
- **축 C는 지금 LOCK 금지**(S9 미측정) — 표시형(B)과 임베딩형(C)의 확정 타이밍이 다르다.

## §7 G-1 미측정 라벨 (측정 전 단정 금지)

- **S9** (전기 수식·기호 bge-m3 hit-rate): 미측정 = **최대 공백·GO 선결**. 현 83.3%는 손해평가 산문 전용. 표시형/임베딩형의 검색 우열은 전부 **추정**.

- **S4** (전기 그림·수식 렌더 필요 문항 비중): 단일 표본(~34/100 이미지), 미재검증.
