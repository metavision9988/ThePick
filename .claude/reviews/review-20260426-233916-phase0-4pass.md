## CRITICAL (4 페르소나 dedupe 후 7건)

### C-1. prevent_X_update 화이트리스트 우회 — 4 페르소나 합의 (silent#1 + sec-S1 + arch-C2 + qa-C1)

**파일**: `migrations/0013_active_view_and_review_decisions.sql:67, 75, 83`

```sql
WHEN OLD.is_current_active = NEW.is_current_active
```

같은 UPDATE 트랜잭션에 `SET is_current_active=0, name='해킹', formula='...'` 동시 → WHEN 절 false (active flip) → ABORT 미발동 → 본문 변조 통과.

특히 **formulas.equation_template** 변조 시 산식 결과 전체 오염 (L3 영역, 북극성 직접 사망).

line 59~61 의 주석이 위험을 인지하나 "application 레이어 강제" 로만 미룸 — DB 마지막 방어선 자기 포기 상태.

**해법**: WHEN 절을 컬럼별 화이트리스트로 재작성:

```sql
WHEN NEW.name IS NOT OLD.name
  OR NEW.formula IS NOT OLD.formula
  OR NEW.page_ref IS NOT OLD.page_ref
  OR NEW.equation_template IS NOT OLD.equation_template
  OR NEW.numeric_value IS NOT OLD.numeric_value
  OR ... (본문 컬럼 명시)
```

### C-2. DELETE 트리거 부재 — silent-failure-hunter 단독

**파일**: `migrations/0001/0003/0004/0013` 모두

`prevent_X_update` 는 있으나 `prevent_X_delete` 가 **없음**. `DELETE FROM knowledge_nodes` / formulas / constants 가 silently 통과 → audit history 사라짐 → SUPERSEDES 엣지 dangling → status_transitions 의 target_id orphan.

Hard Rule 1 의 "UPDATE 금지" 의도와 동일하게 DELETE 도 차단해야.

**해법**: 3 테이블 각각 `BEFORE DELETE ... RAISE(ABORT)` 트리거 추가 (status_transitions / review_decisions 패턴 동일).

### C-3. formulas/constants SUPERSEDES 트리거 부재 — 3 페르소나 합의 (silent#2 + arch-C3 + qa-C2)

**파일**: `migrations/0013_active_view_and_review_decisions.sql:96~108`

knowledge*nodes 만 `mav_supersedes*\*\_deactivate` 트리거. formulas/constants 는 application 레이어 책임이라 주석으로 미룸.

그러나 **packages/** 코드 grep 결과 `is_current_active` 참조 **0건** — application 레이어 enforcement 가 사실상 없음. Loader 가 누락 시 silent drift → formulas 활성 플래그가 두 개 동시에 1 → 운영 RAG 가 구·신 산식 동시 노출 → **산식 결과 비결정성**.

**해법**: (a) formulas/constants 에 동등 트리거 추가 (knowledge_edges 의 from_node/to_node 가 두 테이블 ID 도 참조 가능하게 FK 확장 또는 별도 supersedes 컬럼), 또는 (b) Phase 1 게이트에 invariant 검증 SQL (`SELECT formula_id, COUNT(*) FROM formulas WHERE is_current_active=1 GROUP BY formula_id HAVING COUNT(*)>1 = 0`) 추가.

### C-4. ADR-013 column drift (`relation` ↔ `edge_type`) — system-architect 단독

**파일**: `docs/adr/ADR-013-materialized-active-view.md:28~46`

ADR-013 본문 SQL 예시 4회 `relation` 사용. 실제 schema (0001 line 41) 는 `edge_type`. ADR 을 정본으로 보고 후속 마이그레이션 (0014/0015 KV 캐시 등) 작성 시 **즉시 SQL 에러**.

**해법**: ADR-013 line 28~46 sed 정정 — `relation` → `edge_type`.

### C-5. SUPERSEDES 순환 가드 부재 — quality 단독

**파일**: `migrations/0013_active_view_and_review_decisions.sql:101~108`

A→B 후 B→A SUPERSEDES INSERT 가능. A 비활성, B 비활성 → **활성 노드 0건 → 운영 RAG 데이터 손실**.

`WHERE id = NEW.to_node AND is_current_active = 1` 로 무한 cascade 는 차단 (이미 0이면 no-op) 되나, 두 노드 모두 비활성화 상태 자체는 발생.

**해법**: BEFORE INSERT 가드 트리거 — `WHEN NEW.edge_type='SUPERSEDES' AND EXISTS(SELECT 1 FROM knowledge_edges WHERE from_node=NEW.to_node AND to_node=NEW.from_node AND edge_type='SUPERSEDES') ABORT`.

### C-6. ai-adapter unit test 부재 — 2 페르소나 합의 (qa-C3 + code-reviewer-M2)

**파일**: `packages/ai-adapter/__tests__/` 부재

- production-quality.md "테스트 없이 완료 금지" 직접 위반
- placeholder NOT_IMPLEMENTED 라도 (a) constructor 검증 4분기 (b) `describe()` freeze (c) `sendMessage`/`sendVision` throw 메시지 — 모두 즉시 Golden Test 가능
- Phase 3 본격 구현 전 계약 고정 의무

**해법**: `packages/ai-adapter/__tests__/anthropic-adapter.test.ts` 신설 — vitest. 최소 5 test (constructor 4 + describe 1 + throw 2 = 7).

### C-7. review_decisions 인증 결합 부재 — security 단독

**파일**: `migrations/0013_active_view_and_review_decisions.sql:135, 188~193`

`reviewer_id TEXT NOT NULL` — 단순 NOT NULL/empty 검증만. DB 가 reviewer_id 가 "human session" 인지 "백그라운드 잡" 인지 구분 불가.

공격 시나리오:

1. 운영자 계정 탈취 또는 SQL injection
2. `reviewer_id='system'` + `decision_type=ai_recommendation` INSERT
3. **INSERT-only 의 불변성이 오히려 공격자 편** — 사후 정정 불가

→ Hard Rule 29 (AI 추천 자동 채택 금지) 우회 가능.

**해법**: (a) `reviewer_id` 에 `CHECK(reviewer_id NOT IN ('system','ai','auto','batch'))` (b) 허용 reviewer_id 목록을 별도 테이블 + FK (c) Workers 미들웨어가 세션 기반 reviewer_id 강제 주입 (클라이언트 입력 금지) (d) `ai_recommendation = decision_type` AND human session marker 부재 시 ABORT.

## MAJOR (7건)

### M-1. references_decision_id 자기 참조 차단 부재 (qa)

`decision_type='rollback' AND references_decision_id = id` 가능 → 무한 rollback 체인. `WHEN NEW.references_decision_id = NEW.id` ABORT 트리거.

### M-2. ai_recommendation/ai_confidence 짝(pair) CHECK 부재 (qa)

한쪽만 NULL 인 INSERT 가능 → 무의미. `CHECK ((ai_recommendation IS NULL) = (ai_confidence IS NULL))`.

### M-3. rollback_deadline 형식 검증 0건 (qa)

`'asdf'` 통과 → 만료 비교 silent 실패. `CHECK (datetime(rollback_deadline) IS NOT NULL)`.

### M-4. ontology-registry.json SoT 분열 (code-reviewer)

`node_types` 배열 + `node_types_meta` 객체 키가 동일 SoT 인데 동기화 미강제. 한쪽만 수정 시 침묵 통과. `assertRegistryShape` 에 교차 검증 + TS 타입 추가 의무.

### M-5. describe() Object.freeze 반복 (code-reviewer)

`ResolvedConfig` freeze 후 `describe()` 가 별도 freeze 객체 생성 — SoT 분열 디자인 스멜. `ResolvedConfig` 에 `vendor`/`model` 포함시키고 통합.

### M-6. review_decisions ↔ status_transitions 책임 경계 미문서화 (system-architect)

두 INSERT-only 테이블의 동시 기록 의무인지 단일 진입점인지 불명. ADR 또는 별도 ADR 명시.

### M-7. SUPERSEDES 다중 체인 회귀 테스트 부재 (qa)

A→B→C 시나리오 sqlite3 dry-run 미포함. 정합성은 OK 추정이나 회귀 테스트 의무.
