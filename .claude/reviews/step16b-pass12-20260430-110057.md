### 반론 (Devil's Advocate — 깨질 수 있는 시나리오)

- **시나리오 B 의 in-memory `Map.set` 덮어쓰기 분기 (case A)** — 두 호출이 모두 `selectByRunId=null` 을 같은 시점에 반환하면 두 인스턴스 모두 `insertNewRun` 진입. `in-memory-batch-runs-db.ts:99-103` 의 `if (existing && existing.state === 'completed')` 만 차단하므로, **`existing === undefined` 인 경우 두 번째 호출이 첫 번째 행을 덮어쓰는 race** 가능. JavaScript 단일 스레드라 `Map.set` 자체는 atomic 이지만, 두 `runPipeline` 의 `await selectByRunId → await insertNewRun` 사이에 다른 microtask 가 끼면 두 호출의 첫 번째 INSERT 가 모두 성공 → 행 1개 (덮어쓰기 결과) 라 invariant `length === 1` 은 holds, 그러나 production D1 에서는 0015 PRIMARY KEY 가 두 번째 INSERT 를 RAISE(ABORT). **검증 차이**: in-memory 환경에서는 silent 덮어쓰기, production 에서는 throw → caller 분기 다름. 본 e2e 가 production 동작을 충분히 검증하지 못할 가능성. (이 부분은 plan NG-1 D1 batch atomicity 가정으로 일부 cover, 단 BatchRunsDb 자체의 PRIMARY KEY 동작은 NG-1 범위 외로 보임.)
